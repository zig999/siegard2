# Under a goal

Read before the plan where the goal's condition asks to specify its objective, and at step 3 or
later where a step stopped under a goal.

## What a goal changes

A goal condition naming this skill is the person's ask armed as a standing automation, and it
changes what four stops do — nothing else: «Under a goal condition naming the orchestrating route,
the orchestrating entry point takes the door a derived recommendation names where that door is an
entry point the route invokes, and takes the door a judged choice leaves only as the door decider
returned it, blind to the condition and while the condition's budget of judged doors is not spent.»
(SPEC-006 R7)

Every door taken is one line of the log, on its own,
`decided: <door> — <criterion> — <deciding fact>`, and its commit names the run as every other does.
The plugin's `PreToolUse` hook refuses a commit that adds a line opening with `decided:` or
`recommended:` out of that form, or a judged `decided:` line where no goal armed through the
framework names this initiative: a choice no fact decides, outside such a goal, is handed to the
person and never written as taken. A door the three reserved questions hold — a contradiction, two
readings of one piece of evidence, a finding's worth — is never taken.

The taking is yours; the judgment never is.

## An objective the condition asks to specify

Before the plan, and once: «Under a goal whose condition asks to specify a prose objective, the
orchestrating entry point invokes `/analyse` once, before the plan, over the objective as the person
armed it, and commits the specification root apart.» (SPEC-008 R10)

1. The material is the objective file's text, read whole after its digest is checked against the
   condition; the project root is the condition's.
2. A report opening `stop: no-fact —` or `stop: no-change —` is nothing to specify: write the line
   to the log and plan. Any other stop of `/analyse` ends the run.
3. Where it wrote, run the gate again — `spec.py` over the specification root — and commit the
   specification root, with the ledger `/analyse` answered beside the objective and nothing else, as
   `deliver-scope <slug>: analyse`. A ledger left untracked is a tree the goal's state never reads
   as clean: «That commit takes the ledger the analysis answered beside the objective with it»
   (SPEC-008 R10).
4. Plan with the same objective as the scope.

The report carries what `/analyse`'s own report states for a reviewer: the decided fields per node,
the nodes written, what the increment may have put delivered code in breach of, and the
reconciliation candidates it named. The person reviews this specification after the goal, not
before.

## A task waiting on a re-bind

The door is the one `--outstanding` names: `/plan-work` over the slug, the plan's ordinary
evolution. Take it, commit the work root and the specification root as
`deliver-scope <slug>: rebind <task>`, and resume the loop — «a task waiting on a re-bind by
planning over its slug, each once per task, before the run resumes; a second time over one task is a
stop.» (SPEC-008 R8)

## A delivery that stopped over a fact no node states

`/implement-task`'s report hands the `/plan-work` invocation of the decided-fact route beside the
`/analyse` one. Take the first, commit the work root and the specification root as
`deliver-scope <slug>: decide <task>`, and resume: the task re-delivers against the fact now stated.
Once per task, as above. Where the decider returns the fact as one the specification contradicts,
that is a contradiction, and the run stops on it.

## A derived recommendation

Where a stopping report recommends a door on one of the four derived grounds and that door is
`/plan-work`, `/implement-task` or `/review-change`, take it, with the criterion the report gave.

## A judged choice

A delivery that gave up, an infrastructure failure the diagnosis read twice, a certification refused
again — while the condition's budget of judged doors is not spent. A red no change to the task's own
files can answer is never one: trying the same delivery again cannot reward it, and it ends the run
as `outside-task`.

1. Spawn a `siegard:door-decider` subagent, its judgment at
   `${CLAUDE_PLUGIN_ROOT}/agents/door-decider.md`, handing it four things: the doors — the
   invocation the stopping report handed to try again, and ending the run on this stop — each with
   what it does and what it leaves; the facts each rests on, by path, the runs and the diagnoses
   among them; the condition's scope line quoted, and nothing else of the condition; and the budget
   left. Never the conversation, never the attempts' story, never what ends the goal.
2. Save its return as the subagent's own reply.
3. `chosen` or `excluded` naming the door to try again: take it, write the `decided:` line with the
   rung it named, and count one door of the budget. Anything else — `reserved`, `none`, or the door
   that ends the run — is the stop it was.
4. The budget left is read, never remembered: the condition's state command prints `check budget`,
   the judged `decided:` lines the log gained since the goal began against the budget it pins. A
   judged choice met with the budget spent is a stop of its own.

## A finding the condition's findings policy names

After the review's commit, each finding of the conformance pass whose kind the policy names is
answered «by one corrective increment over the file it names, delivered and reviewed in the same
run, once» (SPEC-008 R9).

1. The review hands no invocation forward, so this is the one invocation you compose, and only from
   the review's record: `/plan-work`'s corrective increment with the file the finding names, the
   finding's own words as the wrong behavior, and the node it names.
2. Commit the plan as `deliver-scope <slug>: correct <file>`, deliver the corrective task as step 3
   does, review the corrective tasks once, and commit.
3. What that review finds is reported, never corrected again.
