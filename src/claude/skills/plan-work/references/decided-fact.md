# The decided-fact increment

Read when the person names a fact a delivery stopped over, with the task that delivery was for.

`/implement-task`'s implementer stopped over a fact no node states, and the stop quoted it. It is
the silence step 4 settles, met later — «a delivery finding that no node states a fact the work
needs» (SPEC-001 R13) — and it is settled the same way: decided by a context that never saw the
task, disclosed in the node's log.

**The invocation names it; it is never inferred.** `/implement-task`'s report hands this invocation
beside an `/analyse` one, both filled with the fact and the task; the choice between them is the
person's. Under a goal the person armed, `/deliver-scope` takes this one.

```
situate → intake → step 4's settlement of the one fact → re-bind the task → validate → report → stop
```

1. **Intake** holds the fact as the stop quoted it, and the task's identity — nothing read in the
   source, for the reason `references/corrective.md` states.
2. **Settle the one fact as `references/unstated.md` does.** Grep the specification root for its
   terms first: a node that already states it means the task's candidates missed it, and the answer
   is the re-bind below, with no decider spawned. Otherwise spawn one
   `siegard:unstated-fact-decider` handed exactly what step 4 hands it — the fact, the impact set
   of the nodes the task implements, the intake paths and the specification schema paths — never
   the task. A return of `contradicted` is a contradiction between the scope and the
   specification: write nothing, and stop with the node and its statement quoted.
3. **Bind the task again**, through step 4's binder, so its `implements` and notes see the
   specification as it now stands, and rewrite the task file from that return. `/implement-task`
   then delivers it as a re-delivery.

The survey and the decomposition do not run: the task exists.
