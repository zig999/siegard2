# A knowledge change in a governed repository

A downstream-shaped case: an order-to-cash domain already holds an order lifecycle and an invoice,
and the rule that a cancelled order cannot be invoiced is missing. One change request runs the full
default path of `specs/0001-knowledge-object-driven-development.md` and reaches a maintainer's
acceptance.

This is the second workflow fixture, and it exists for what the first one does not cover.

## What it holds

| Path | What it is |
|---|---|
| `inputs/run.json` | the ordered steps, with every identifier and instant stated |
| `inputs/events/*.json` | the events a caller records directly |
| `inputs/impact-analysis.json` | an `update` verdict, produced by `impact-analyst`, validated at the boundary |
| `event-log.jsonl` | **derived.** The log the steps produce |
| `derived-state.json` | **derived.** The state replayed from that log |

Both derived files are regenerated by `python3 scripts/replay_workflow.py` and verified by
`scripts/replay_workflow.py --check` in `make validate`. Do not hand-edit either.

## The recorded path

```
seq  phase                 outcome     how it was recorded
1    change-request        recorded    caller, stating attempt_limit 3
2    impact-analysis       update      consumed from impact-analysis/1
3    context-resolution    resolved    caller
4    specification-delta   recorded    caller
5    implementation        updated     caller
6    validation            passed      caller, with evidence
7    acceptance            accepted    caller, decided_by a maintainer
```

## What it is evidence for

- **The `update` transition, which `knowledge-change-loop` never takes.** That fixture runs a
  `create` verdict. `specs/0001` R4 fixes three, and the guard table has a row for each; a fixture
  set exercising two of three left one row asserted and unrun.
- **`impact-analyst` is the named producer of `impact-analysis/1`.** The contract had a consumer and
  no producer: `scripts/orchestrate.py` records that its entry carries no `producer` key because R4
  requires the artifact rather than a particular producer of it. An agent now exists for it, and this
  fixture is what makes the generator ship it — `specs/0006` R11 admits a capability when a fixture
  exercises it, and R14 keeps a `proposed` one out of the distribution entirely.
- **A workflow with no failure and no recovery.** `knowledge-change-loop` runs one validation failure
  and one recovery under an attempt limit. This one passes first time, which is the other direction
  of the same guard: `attempts` reaches 1 of 3 rather than exhausting the limit.
- **An implementation phase with no producer contract.** The change is a knowledge object, and no
  agent produces one yet, so seq 5 is a recorded event naming its subject rather than a consumed
  artifact. That is what the phase honestly is today, and it is the shape that changes when a
  knowledge-object producer arrives.

## What it is not evidence for

Named rather than left to be assumed:

- **No agent ran.** `impact-analyst` is a recorded producer here, not an observed one — exactly the
  status `concept-author` has in `knowledge-change-loop`. What is proven is that a conforming result
  from that producer drives the loop, not that the agent produces a conforming result.
- **Nothing was installed or loaded.** The distribution is generated and can be installed into a
  directory — `tests/test_install.py` covers idempotence, divergence, and shadowing — but no Claude
  Code session has resolved `/siegard:knowledge-change` or delegated to either agent. That is
  ADR-0009 condition 2, and it remains open.
- **There is no knowledge base here.** The paths in `subject` and in `implicated` are the shape a
  governed repository would carry. `scripts/validate_knowledge.py`, `project_knowledge.py`, and
  `measure_ontology.py` all discover a base at `fixtures/*/knowledge`, so adding one here would
  commit this fixture to a full conforming ontology with derived projections. That belongs with the
  agent that authors knowledge objects, which does not exist yet.
- **The evidence in seq 6 is illustrative.** It names `bin/validate_knowledge.py`, which the
  distribution does not ship — the knowledge validators are not in `SHIPPED_EXECUTABLES` today. The
  event records what a governed repository's validation step would report, and the guard checks that
  evidence agrees with the verdict it accompanies, not that the command exists.
