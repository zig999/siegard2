# The knowledge change loop

A downstream-shaped case: a billing domain needs the term *dunning* defined before its invoice
lifecycle can reference it. One change request runs the full default path of
`specs/0001-knowledge-object-driven-development.md`, fails validation once, recovers, and reaches a
maintainer's acceptance.

This is the fixture for `docs/bootstrap.md` stage 2 — the first workflow loop, over knowledge only.
It exercises the orchestrator, the event log, the workflow-state derivation, and the transition guard
as one path rather than four units.

## What it holds

| Path | What it is |
|---|---|
| `inputs/run.json` | the ordered steps, with every identifier and instant stated |
| `inputs/events/*.json` | the events a caller records directly |
| `inputs/impact-analysis.json` | the impact verdict, validated at the boundary and consumed |
| `inputs/concept-authoring-result-{1,2}.json` | two `concept-author` results, validated and consumed |
| `event-log.jsonl` | **derived.** The log the steps produce |
| `derived-state.json` | **derived.** The state replayed from that log |

Both derived files are regenerated by `python3 scripts/replay_workflow.py` and verified by
`scripts/replay_workflow.py --check` in `make validate`. Do not hand-edit either: the check compares
them against a fresh replay and reports a mismatch as a defect.

Every identifier and timestamp is stated in `inputs/`, never minted at run time. A log whose ids came
from a clock could not be regenerated and compared, which would make the reproducibility claim
untestable.

## The recorded path

```
seq  phase                 outcome     how it was recorded
1    change-request        recorded    caller, stating attempt_limit 2
2    impact-analysis       create      consumed from impact-analysis/1
3    context-resolution    resolved    caller
4    specification-delta   recorded    caller
5    implementation        authored    consumed from concept-authoring-result/1
6    validation            failed      caller, with evidence
7    implementation        updated     consumed from concept-authoring-result/1
8    validation            passed      caller, with evidence
9    acceptance            accepted    caller, decided_by a maintainer
```

## What it is evidence for

- **All seven phases run.** `specs/0001` R2 fixes the default path and states escalation inserts
  phases and never removes one. `docs/bootstrap.md` stage 2 names this loop in five words —
  `request → impact analysis → knowledge authoring → validation → acceptance` — and that is shorthand
  for the same seven, not a shorter path. Here context resolution is *degenerate*, not skipped: in a
  bundle this small the impact set already is the context, so the phase resolves trivially and records
  that it did. Knowledge authoring is the implementation phase, because in a knowledge-only change the
  authored knowledge is what the change produces.
- **A transition is a lookup, never an interpretation** (R5). Three events came from
  `orchestrate.py consume`, which reads a closed field — `verdict` on one contract, `state` on the
  other — from an artifact that passed its schema at the boundary. Nothing in the orchestrator reads
  prose, and the fixture would fail if it did: the results carry no prose to read.
- **The boundary rejects rather than repairs** (R6). This is the fixture that closed the gap
  `schemas/concept-authoring-result.json` declared in its own description, where the boundary check
  was named as arriving with the orchestrator.
- **A validation failure returns to implementation under a stated limit** (R7). Attempt 1 fails,
  attempt 2 passes, and the limit came from the workflow's own opening event rather than from a
  framework default. With the limit used up, the guard refuses `failed` and requires `exhausted`,
  which is terminal — `tests/test_workflow_events.py` covers both directions.
- **State is derived, never stored** (R8). `derived-state.json` is replayed from the log; the tests
  assert that shuffling the file order changes nothing, because ordering is `seq`.
- **No workflow accepts its own output** (R21). The acceptance event carries `decided_by`, and the
  contract rejects an acceptance without it. `orchestrate.py` has no path that emits one.
- **Validation carries evidence** (R22), and the guard rejects evidence that disagrees with the
  verdict it accompanies.

## What it is not evidence for

Named rather than left to be assumed:

- **The agent never ran.** `concept-author` is inert in this repository. The two results here are
  recorded artifacts, so what is proven is that a conforming result drives the loop and a malformed
  one is rejected — not that the agent produces a conforming result. That needs the generator and an
  installed component, which is `docs/bootstrap.md` open question 2 and ADR-0009 condition 2.
- **The skill never ran either.** `src/claude/skills/knowledge-change/SKILL.md` is the entry point
  this path is designed for, and it is inert here for the same reason.
- **No context package exists.** Context resolution records that it resolved; it produces no artifact,
  because `specs/0001` R11's context package has no contract yet and the phase that needs one has not
  arrived. The same holds for the specification delta: nothing consumes it to choose a transition, so
  `.claude/rules/contracts.md` does not yet require a schema for it.
- **The knowledge bundle is not here.** The paths in `files_changed` and in `implicated` are the shape
  a governed repository would carry; this fixture exercises the workflow, not the bundle. The bundle
  side is `fixtures/knowledge-two-context/`.
- **`none` and `blocked` paths are not in this log.** Both are covered by tests rather than by a second
  recorded history, because a fixture per branch would multiply files without adding evidence.
